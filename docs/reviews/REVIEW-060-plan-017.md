## 实施前必须在现有 Item 内落实的合同

以下是既有范围的验收解释，不追加新的产品目标或流程制品。

1. **信任与正确性分开。** 确定性检查可验证大小、路径、身份、作用域及权限，不能据此证明 Agent 生成的断言足以覆盖目标。1.1/2.2 应说明断言冻结时点、独立审查和变更责任；不得允许实现者为通过测试自行削弱标准或覆盖基线。
2. **默认自主与必要 Gate 一致。** 缺少用户验收脚本本身不能重新变成必须由用户写测试的阻塞；同样不能给所有生成验证器机械增加一次无条件确认。应明确现有本地授权可自动继续的情况，以及网络、Secret、外部副作用或真正权限扩张需要确认的情况。
3. **用户材料按类型消费。** 显式 Markdown 是目标约束和验收依据，不自动获得执行权限；配置脚本的内容身份、声明覆盖和受信执行边界必须可审计。与用户硬约束冲突或材料缺失应给出可执行恢复动作，不能静默忽略或以生成标准替换。
4. **失败不能降低完成条件。** 空项目允许先生成会失败的业务断言，再由实现满足它；断言失败、无法执行、缺少必要依赖和超出权限应保持不同反馈。不能把命令退出零、格式检查或模型自评当作业务完成证据。3.2 应至少保留错误实现、无效断言或假通过路径的拒绝负例。
5. **恢复沿同一身份闭环。** 2.3 应对账 Goal Revision、配置与材料 hash、验收基线和最终 Tree；重启不能重新生成较弱标准，批准不能跨 Goal 或跨输入复用。已有 WAITING Goal 的继续方式应进入 3.1 的恢复说明，无需要求用户重新创建项目。
6. **真实结果必须是可运行交付。** 3.3 应记录实际 Provider、生成源文件、启动方式和移动、进食、碰撞、重新开始的可复核运行结果，并核对最终 Evidence 指向相同 Tree；仅有页面文件或无错误日志不满足本次用户体验验收。
